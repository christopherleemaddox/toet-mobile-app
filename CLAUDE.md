# TOET Mobile App — daily encouragement cards

## What it is
A Bible-based affirmation/encouragement card app: 7 categories, 93 topics, **1,861 cards** (corrected 2026-08-07 — verified by parsing `window.CARDS`; an older "461" figure was stale documentation, not a real count). Each card gives a "truth" (a personalized affirmation grounded in a verse), the verse/reference, and a related prayer. **No free/premium split** — every user gets full access to everything. There was an earlier premium-tier direction (see "Decided" below); Christopher deliberately abandoned it to keep the app simple.

Professional recorded narration was ruled out as infeasible at this content volume (1,841 cards × 3 fields each, and it would break the single-file no-backend architecture privacy is built on) — the shipped answer instead uses the device's own built-in text-to-speech (the browser's `SpeechSynthesisUtterance` API), so it costs nothing, needs no hosting, and works with zero changes to how the app is built or deployed. This closes the *feature* gap, not the *warmth* gap — a synthesized voice, not a recorded narrator — which is a real, known tradeoff, not an oversight.
  - New icon button (▶ / ■ toggle, same circular style as the existing heart/share buttons) reads the current card's verse, truth, and prayer aloud in sequence, trailing punctuation on each segment cleaned up first so it doesn't stutter on a double period. Verified in-browser by instrumenting `speechSynthesis.speak`/`.cancel` and confirming the exact utterance text and cancel-on-close behavior, not just that the button visually toggled.
  - Blueprint updated to match: R5 ("Action Row") now documents the new button and its mockup shows the third circle.
  - **Voice quality follow-up, same day.** Christopher's first listen found the voice too robotic — the code wasn't picking a voice at all, just taking whatever the browser's default happened to be. Added `pickVoice()`: reads `speechSynthesis.getVoices()` at speak time and scores them (favors names containing "enhanced"/"premium"/"natural"/"neural", and on-device voices over network ones), picks the best match, falls back to the untouched default if the device reports zero voices (verified this path doesn't throw). This is still the free, on-device tier — it can reduce the robotic quality using whatever's already installed on Christopher's phone, but it is not the same as real recorded/AI-generated narration. That bigger option (pre-generate real audio for all 1,841 cards with a paid AI voice service, host as static files to keep the no-live-calls privacy promise intact) was discussed and deliberately not started — real cost, real file size, Christopher's call if the free tier isn't good enough.

## Competitive research (2026-08-07) — for reference, nothing acted on yet
Christopher asked for a comparison against the daily-devotional / Bible-verse app category, via Tavily research — explicitly research-only, no changes made to the app from this. Revisit when he's ready to decide what (if anything) to act on.

**Apps researched:** YouVersion, Glorify, Pray.com, Abide, Dwell, First5, Our Daily Bread, She Reads Truth.

**Where this app already compares favorably:**
- **Privacy** — no account, no tracking, nothing ever leaves the device. Genuinely uncommon: Dwell's own Play Store listing admits it collects personal/financial data, unencrypted.
- **No paywall** — Abide, Glorify, and Pray.com all gate real content behind subscriptions; this app gives everyone everything, free, permanently (see "No premium tier" above). Real goodwill differentiator, though it means no built-in revenue path — a separate, later conversation.
- **The personalized "truth" line** — verse + an affirmation written in the user's own voice/name. Nothing in the research showed a competitor pairing content this way.
- **Reading-mode flexibility** — scroll/story/swipe/tabs for reading a single card. Competitors mostly offer one fixed format.
- **Accessibility** — the research couldn't even find evidence competitors document accessibility work at all, let alone the level just shipped here (real keyboard buttons, measured WCAG contrast).

**Where the category is ahead of this app:**
- **Audio — the biggest gap.** Dwell is entirely audio-first (narrator selection, looping, a "Reflect" pause feature). Abide is guided meditation audio. First5 has dramatized audio. Pray.com has done 100M+ podcast downloads. This app has no audio anywhere.
- **Habit/streak tracking.** YouVersion's core growth engine is a visible daily-streak counter. This app has "Draw Another" and a daily word, but nothing that visibly rewards returning tomorrow.
- **Scale of structured content.** YouVersion has multi-day reading *plans*; this app is single-card daily encouragement — a different product shape, not strictly a gap, but worth naming so it doesn't read as a miss.

**On visual design specifically:** the research came back thin — most competitors don't publish real design specs, and nothing suggested an industry-standard palette being missed. The current warm cream/gold palette is a coherent, defensible choice on its own; nothing found here says it needs to change.

**Bottom line if this gets picked back up:** audio is the single feature most likely to matter if Christopher ever wants to compete more directly with the category leaders. Habit/streak mechanics would be the second thing to consider. Neither is started — this section is findings only, not a plan.

## Crisis resources — built 2026-08-08
Closes the gap the pre-launch audit flagged. Confirmed first by grepping the real decoded source: before this change there was not one occurrence of `988`, `crisis`, `hotline`, `emergency`, or `professional` anywhere in the template or the app logic.

**Three parts, all static text — nothing about this makes a network call, so the "nothing ever leaves this device" promise is untouched.**
1. **A new "If you need help right now" screen** (Blueprint codes `H1`–`H8`), modeled directly on the Privacy screen's pattern. Contents: 911 for immediate danger, 988 Suicide and Crisis Lifeline (call **and** text), Crisis Text Line (HOME to 741741), findahelpline.com for outside the US, and a closing section stating that a doctor, counselor, or pastor takes nothing away from someone's faith. Numbers are real tappable `tel:` / `sms:` links, so one tap dials or opens a text on a phone.
2. **A Settings entry point** (`S25`, "IF YOU NEED HELP"), sitting directly after `S2`/Privacy.
3. **A quiet conditional line in the reader** (`R11`): *"If today is heavier than a hard day, help is here →"*. **Deliberately only on 15 of the 93 topics** — Hopelessness, Sadness, Grief, Loneliness, Abandonment, Rejection, Weariness, Trouble, Overwhelmed, Burnout, Anxiety, Shame, Condemnation, Self-Worth, Anger at God. The reasoning matters and should not be quietly undone: on all 93 it becomes furniture people stop seeing; on the topics where someone in real trouble actually lands, it still registers. The list is one inline array in the `readerHelpLine` binding, easy to edit.

**Two things were considered and deliberately rejected**, so they do not get "discovered" as oversights later:
- **No pop-up triggered by tapping a heavy topic or check-in chip.** It misfires constantly (people pick Grief for a pet, Hopelessness about a job) and turns a gentle self-reflection into something that feels surveilled. Always-present and quiet beats reactive and inferential.
- **No blocking modal or "are you okay?" interstitial.** Nothing gets between a user and their word.

**Implementation notes.** All four reader modes share one `rc` computation, so `R11` needed editing in exactly one place — unlike the Read Aloud button's four near-duplicate action rows. The help screen sits at `z-index:40`, above both the reader (20) and the inline Settings view, and `openHelp` deliberately does **not** clear `settings` or `reader` state, so `← Back` returns the user exactly where they were. (The older Privacy screen does clear `settings`, so its "← Back to Settings" label is slightly untrue — pre-existing, not worth churning.)

**Tap-tested by Christopher on his own iPhone, 2026-08-08, after deploy — all three work end to end:** Call 988 opens the phone dialer, Text HOME to 741741 opens Messages **with the word HOME already prefilled**, and findahelpline.com loads in the browser.

**Do not "correct" the Crisis Text Line link to `?body=`.** It is written `sms:741741&body=HOME` with an ampersand. RFC 5724 specifies `?body=`, so that looks like a bug on sight — but the ampersand form is what Apple has historically honored, and it was confirmed prefilling correctly on Christopher's actual iPhone on 2026-08-08. Changing it to match the spec would be an untested change to a crisis link. If it ever does need changing, re-test on a real device first; prefill saves someone in a bad moment from having to remember a specific word. This was the one part Claude could not verify itself (the numbers were written from model knowledge, not checked against a live source in-session), so it was handed to Christopher deliberately rather than assumed. **Re-check periodically**, and re-check any time this screen is edited — wrong crisis contact info is worse than none.

**Verified in-browser before shipping**, both themes, zero console errors: both entry points open the screen; all five `tel:`/`sms:`/`https:` links carry the right hrefs; every new control is a real focusable element (`tabIndex` 0); and the topic gating was tested positively **and negatively** — line present on Grief / Shame / Anger at God, absent on Gratitude / Wisdom / Praise. The negative half is the one that matters; a line that showed everywhere would have looked like a success.

**Content rule, now checked rather than asserted: no card's `truth` or `prayer` may imply that faith replaces clinical help.** All 1,861 cards were scanned against 8 patterns (clinical nouns, sufficiency claims, "just pray", "don't need", "instead of seeking", self-harm language, cure claims, shame-for-asking). **Zero violations.** The 7 hits that surfaced are all benign metaphor and should be left alone: #818 "pleasant words… I can dispense medicine", #642 "God's first treatment for His burned-out prophet was food and sleep", #1110/#1113/#1115 (Healing, word-as-medicine), #1569 "every offense gets one treatment or the other". The scanner carried a planted negative-control card that 4 of the 8 patterns caught, so the clean result was proven rather than assumed — and the first version of the parser silently matched **0** cards, which would have reported a false all-clear if the script had not printed its parsed count. Re-run this whenever cards are added.

## New "Praise" topic — built and shipped 2026-08-07
Grew out of the repetition audit below: cards #372 and #1187 both sat in **Gratitude** with near-identical verse text. Christopher chose to move #1187 to a new **Praise** topic and fill that topic out properly, rather than accept a one-card topic or just swap a verse. **Result: 93 topics, 1,861 cards.** Praise 20, Gratitude restored to 20, Worship untouched at 20.

**How the content was made, and the one rule that matters most:** verse text was NEVER written by a model. Agents proposed and wrote around *references* only; the actual Scripture was pulled programmatically from the local KJV corpus and injected by the insert script. That makes "word for word" true by construction instead of by hope. Repeat this pattern for any future card generation.

**Theological screening was a hard gate, and it earned its keep.** Candidate verses came from a keyword search for praise/magnify/extol/glorify/exalt, which is naive and pulls in verses where those words are used for idols, self-exaltation, or judgment. Screening agents rejected 11 of 39, including several a manual pre-filter had missed: 1 Peter 5:6 (the *human* is exalted there, not God), Ephesians 1:14 (a grammatical fragment beginning "Which"), Matthew 21:16 (opens mid-dialogue), Malachi 1:5 (depends on a judgment oracle against Edom), Judges 5:2 (ties praise to military vengeance). Never skip this step for a faith product.

**The insert script (`insert_cards.py` pattern) refuses to write unless every gate passes:** reference not already used, no em/en dashes, curly apostrophes only, prayer ends exactly "Amen.", no duplicate truth/prayer against existing cards or within the new batch, word counts in range, and a full re-parse confirming the expected card count after the edit.

**A fix that recreated the same problem, caught only by re-running the audit.** Moving #1187 into Praise solved the Gratitude collision, but the writing agents independently selected Psalm 106:1, which is near-identical to #1187's 1 Chronicles 16:34 — the identical collision, now inside Praise. The duplicate audit caught it; it was swapped for Psalm 95:1 (which also filled a genuine gap: a "joyful noise, not a good voice" invitation). **Lesson: after fixing a duplication problem by moving content, re-run the duplicate audit on the destination, not just the source.**

## Scripture accuracy — verified, not assumed (2026-08-07)
The brand rule is that quoted Scripture is word-for-word. That was previously a promise resting on trust; it is now checked. **All 1,841 cards were verified against a public-domain KJV corpus (66 JSON files, `github.com/aruljohn/Bible-kjv`): 1,841 exact matches, 0 wording differences, 0 reference errors.** Both things were checked, not just one: the `verse` text matches the KJV exactly (after normalizing curly quotes and whitespace), and every `ref` points at a real book/chapter/verse that genuinely contains that text. Multi-verse refs (e.g. `Philippians 4:6-7`) are joined and compared as a unit.

The check is saved as the **`verify-kjv`** skill (`.claude/skills/verify-kjv/`) so it is re-runnable, since cards will be added over time. The 5MB KJV corpus is deliberately not committed (keeps the repo lean) — the skill documents how to re-download it, and doing so needs Christopher's OK like any download.

**A clean 100% pass was treated as suspicious and proven, not accepted.** The checker was run against deliberately corrupted copies first, and correctly caught a single-word swap (`hath` → `has`), a dropped clause, a valid-but-wrong reference, and a nonexistent reference. Worth repeating that discipline on any future run: a broken comparison and a perfect result look identical from the outside. (One injected "fault" during that test was a no-op — it replaced a word that wasn't in that verse — which briefly looked like a checker miss and wasn't. Check that the corruption actually corrupted something.)

**What this does NOT cover:** whether a card's `truth` affirmation is a sound application of its verse in context. That is a theological judgment, not a string comparison, and needs a pastor or elder to review a sample. Flagged as the single highest-consequence unchecked risk in the app, since a misapplied verse damages brand trust permanently in a way a design flaw does not.

## Card repetition audit — clean (2026-08-07)
Second half of the content audit, companion to the Scripture check above. Hand-built card libraries usually repeat themselves as they grow; this one does not. **Zero duplicate `truth` lines and zero duplicate `prayer` lines across all 1,841 cards.** The highest genuine similarity between any two cards anywhere is 0.689 for truths and 0.788 for prayers, both comfortably below duplicate territory. Saved as the **`audit-card-content`** skill so it can be re-run as cards are added.

Same discipline as the KJV check: a clean result was proven, not assumed. The detector has a built-in negative control that plants an exact copy and a lightly-reworded copy of a real card; both were caught (1.000 and 0.957).

**Repeated verse text turned out not to be a defect.** Four groups of cards share verse wording, but every single one is a genuinely different Scripture reference whose wording the Bible itself repeats (Psalm 42:5 vs 42:11, Matthew 25:21 vs 25:23, Psalm 107:1 vs 1 Chronicles 16:34 vs Psalm 136:1, Lamentations 3:22 vs 3:22-23), and each card's truth and prayer take a different angle. Worth remembering on future runs before "fixing" something that isn't broken.

**One genuine collision, Christopher's call:** cards #372 and #1187 are both in the **Gratitude** topic with near-identical verse text. Different references and different writing, but someone browsing Gratitude meets the same words twice. Every other overlap spans two different topics, so it is unlikely to be hit in one sitting. Options are to move #1187 to another topic (its truth leans on it being the oldest chorus in Israel's songbook, so Worship or Praise fits), swap its verse, or accept it as legitimately two different references.

**Structural note, deliberately not treated as a defect:** 100% of prayers end "Amen.", 86% open with "Lord," or "Father,", and 99.6% are two or three sentences. That reads as formula on a spreadsheet but addressing God and closing with Amen is what prayer *is*, and liturgical repetition is a feature rather than an AI tell. The middle of each prayer genuinely varies, which is the part that matters. Flagged here mainly so a future session doesn't "discover" it and try to fix it.

## App-improvement tooling research (2026-08-07) — findings only, mostly not acted on
Christopher asked for tools that could audit the app and recommend visual, flow, and emotional-attachment improvements. Researched via Tavily across six tool categories with adversarial fact-checking. Two of the research's own claims were wrong and were corrected before use: it said the repo wasn't under version control (it is) and recommended adding data export/import (already shipped).

**The privacy trap, the single most important finding.** Nearly every popular UX tool works by pasting a tracking script into the page. Adopting one would force retracting the "no analytics, no tracking, nothing ever leaves this device" line on the app's own Privacy screen, which is the product's headline differentiator. **Microsoft Clarity** is the one that will be recommended first (free forever, no limits) and its terms permit using collected data for advertising profiles; on an app that records which Bible topics someone opens (legally sensitive religious data in most jurisdictions) that is a reversal, not a compromise. Same verdict for Hotjar and PostHog. The subtle trap is the privacy-first analytics crowd (Plausible, Fathom, Simple Analytics, Umami): they sound compatible but are not, because the promise is not "we collect no personal data," it is "nothing ever leaves this device," and one pageview ping falsifies it. Self-hosting changes who receives the data, not that it left. **Decided: do not add any of these.** Netlify's own ~$9/month analytics is privacy-safe but pointless here (reports per URL, the whole app is one URL, and the service worker means repeat visits never reach Netlify).

**Most tools are also useless at this stage regardless of privacy**, because the site is password-gated with essentially one user, and analytics needs traffic volume to say anything.

**What to actually do, when Christopher is ready:** three to five real people using the app in front of him, one at a time, on his unlocked phone, while he says nothing. One task ("find something for when you're anxious, and read it"), no demoing, no rescuing, write down every hesitation and wrong tap. Free, one afternoon, and the only thing that can answer the emotional-attachment question. Caveat worth repeating to him: people from his own congregation will soften criticism because criticising something framed as ministry feels like criticising the ministry, so recruit from a different church or have someone else run the session while he watches.

**Free and privacy-safe tools that do work now:** the WAVE browser extension (runs entirely in-browser so it works behind the password gate, and draws problems on the page rather than listing error codes); Chrome DevTools Lighthouse in Snapshot mode (untick "Clear storage" first or it wipes the day counter and reading progress); Chrome's colour-vision simulation (a warm palette going muddy for a colourblind reader reads as cheap rather than calm); and his own iPhone at the largest text setting, which older churchgoers use constantly and which is the likeliest thing to break a fixed-height card.

**Two real gaps verified directly in the source. The first is now closed (see "Crisis resources" below); the second is still open:**
- ~~**No crisis resources anywhere in the app.**~~ **Closed 2026-08-08** — see the "Crisis resources" section below. The original finding stands as written: topics like grief, despair and hopelessness get opened by people in genuine trouble, and the no-backend design meant nothing was there.

**Still unchecked and highest-consequence:** whether each card's affirmation is a sound application of its verse *in context*.
