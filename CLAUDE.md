# TOET Mobile App — daily encouragement cards

## What it is
A Bible-based affirmation/encouragement card app: 7 categories, 93 topics, **1,861 cards** (corrected 2026-08-07 — verified by parsing `window.CARDS`; an older "461" figure was stale documentation, not a real count). Each card gives a "truth" (a personalized affirmation grounded in a verse), the verse/reference, and a related prayer. **No free/premium split** — every user gets full access to everything. There was an earlier premium-tier direction (see "Decided" below); Christopher deliberately abandoned it to keep the app simple.

## Competitive research (2026-08-07) — for reference, nothing acted on yet
Christopher asked for a comparison against the daily-devotional / Bible-verse app category, via Tavily research — explicitly research-only, no changes made to the app from this. Revisit when he's ready to decide what (if anything) to act on.

**Apps researched:** YouVersion, Glorify, Pray.com, Abide, Dwell, First5, Our Daily Bread, She Reads Truth.

**Where this app already compares favorably:**
- **Privacy** — no account, no tracking, nothing ever leaves the device. Genuinely uncommon: Dwell's own Play Store listing admits it collects personal/financial data, unencrypted.
- **No paywall** — Abide, Glorify, and Pray.com all gate real content behind subscriptions; this app gives everyone everything, free, permanently (see "No premium tier" above). Real goodwill differentiator, though it means no built-in revenue path — a separate, later conversation.
- **The personalized "truth" line** — verse + an affirmation written in the user's own voice/name. Nothing in the research showed a competitor pairing content this way.
- **Reading-mode flexibility** — scroll/story/swipe/tabs for reading a single card. Competitors mostly offer one fixed format.
- **Accessibility** — the research couldn't even find evidence competitors document accessibility work at all, let alone the level just shipped here (real keyboard buttons, measured WCAG contrast).

**Where the category is ahead of this app:**
- **Audio — the biggest gap.** Dwell is entirely audio-first (narrator selection, looping, a "Reflect" pause feature). Abide is guided meditation audio. First5 has dramatized audio. Pray.com has done 100M+ podcast downloads. This app has no audio anywhere.
- **Habit/streak tracking.** YouVersion's core growth engine is a visible daily-streak counter. This app has "Draw Another" and a daily word, but nothing that visibly rewards returning tomorrow.
- **Scale of structured content.** YouVersion has multi-day reading *plans*; this app is single-card daily encouragement — a different product shape, not strictly a gap, but worth naming so it doesn't read as a miss.

**On visual design specifically:** the research came back thin — most competitors don't publish real design specs, and nothing suggested an industry-standard palette being missed. The current warm cream/gold palette is a coherent, defensible choice on its own; nothing found here says it needs to change.

## Christopher now runs a second, parallel Claude Code session on this repo — expect real git conflicts (2026-08-08)
Discovered mid-session: `git push` was rejected because `origin/main` had two commits neither of us had seen, both authored by a separate "Local" Claude Code session (the one unblocked earlier the same day by fixing the git/Xcode setup on Christopher's laptop) — "Add domain to plain-text card shares (#1)" and "Share via Messages now sends the card image + an interactive link (#2)". Real, legitimate work, not noise: don't assume an unexpected remote commit is stale or safe to discard. Investigate what it actually is before doing anything with it.

**`Live Build/index.html` is a single JSON-escaped template string, so `git merge` conflicts even when the two changes touch completely unrelated JS functions.** Both sessions' edits landed as small, semantically-separate diffs (a domain string in `shareText`, an image+link path in `shareCardImage`, vs. this session's fix inside `componentDidMount`) — but git's line-based diff sees them as colliding on the same enormous line, because the whole template is one long escaped string with no real line breaks matching the JS structure. **Never resolve a conflict in this file by hand-editing the `<<<<<<<`/`=======`/`>>>>>>>` markers** — that means splicing raw text inside a massive JSON-escaped blob, exactly the kind of edit the `read-dc-bundle`/`edit-app-safely` skills exist to prevent.

**The actual resolution path:** abort the merge (`git merge --abort`), confirm your own fix's anchor strings are still unique in `origin/main`'s version of the file (they will be, unless the other session touched the exact same function), decode `origin/main`'s real file, re-run your own fix script against *that* as the new base, verify with preflight and a live browser check that both changes coexist, then finish the merge with `git merge -s ours origin/main` followed by `git commit --amend` with the real reconciled file staged. This produces a normal two-parent merge commit with correct, verified content — not a blind pick of "theirs" or "mine."

## Added: PIN/Pattern App Lock — real protection, not a deterrent (2026-08-10)
Christopher asked for the same PIN/pattern App Lock already built for Memory App and Study App, both earlier the same day. **This app's only prior "lock" concept was a different thing** — the pre-launch Coming Soon tester gate (hardcoded plaintext test codes, no re-lock, no keypad/pattern), explicitly documented above as not real protection. **Same crypto/rate-limiting design as Memory App and Study App, reused exactly, not re-derived**: PBKDF2-SHA256 (`crypto.subtle`, 300,000 iterations, random salt) — only `salt`/`hash` ever stored in the new `toet.lock` key (matching this app's own `toet.*` convention), never a raw PIN/pattern. Escalating, persisted lockout (5 fails → 30s, 10 → 2min, 15 → 5min, 20+ → 15min cap), checked before hashing so a locked-out guess costs nothing. PIN is a fixed 6-digit custom keypad with dot indicators, auto-submit on the 6th digit. Pattern is a 3×3 SVG grid, minimum 4 dots — the known `aspect-ratio:1/1` fix (an SVG with only `width:100%` renders 0×0 in some environments, breaking dot-hit-detection) was applied from the start rather than rediscovered.

**Integration is genuinely different from the other two apps, because this app's architecture is different from both of them.** Mobile App is a single-page React-class DC-runtime bundle with no router — screens are boolean/enum state flags computed by one big `renderVals()`, not hash-routed screens (Study App) or a static-HTML-plus-overlay (Memory App). It already had one full-screen gate of the right shape — the Coming Soon overlay — so the new lock screen copies that exact convention (same wordmark treatment, same `z-index:90`, same inline-error pattern) instead of inventing a new one:

- **Async is scoped tightly to the lock code only** (`attemptUnlock`/`deriveHash`/`_onLockCapture` are the only `async` methods) — `renderVals()` and the rest of the app stay fully synchronous, same discipline the other two ports used.
- **Pattern drawing is fully state-driven, not direct DOM manipulation** — a deliberate deviation from Study App's raw-DOM approach. Study App owns its DOM directly (`main.innerHTML = ...`), so writing straight to a `<path>` element during a drag is safe there.
